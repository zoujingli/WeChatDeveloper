# 领域文档

本仓库采用单上下文（`single-context`）领域文档布局。领域文档用于统一项目专有语言，并保存少量真正需要长期解释的架构决策。

## 开始分析前

开始分析代码或设计变更前，按需读取：

- 根目录的 `CONTEXT.md`；
- `docs/adr/` 中与当前工作区域相关的 ADR。

这些文件或目录不存在时继续工作，不得仅为补齐结构而创建空文件。`domain-modeling` 技能会在术语或决策真正确定后按需创建它们。

## 文件布局

```text
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-example-decision.md
│       └── 0002-another-decision.md
└── src/
```

- `CONTEXT.md` 是项目专有术语表，不是规格、草稿或实现说明。
- `docs/adr/NNNN-slug.md` 每份文件只记录一个架构决策。
- 术语表和 ADR 均按需创建，不预建空文件或空目录。

## 使用规范术语

Issue 标题、规格、设计提案、测试名称和代码中的领域概念，应采用 `CONTEXT.md` 定义的规范术语，避免使用其中明确列出的同义词。

如果所需概念尚未出现在术语表中，应先判断它是否确实属于本项目的专有语言；只有真实缺口才交由 `domain-modeling` 补充。

## 记录 ADR 的条件

只有同时满足以下条件的决定才记录 ADR：

1. **难以逆转**：以后改变决定会产生明显成本；
2. **缺少背景会令人意外**：未来维护者仅阅读代码无法理解为什么这样设计；
3. **存在真实权衡**：曾有合理替代方案，并基于明确理由作出选择。

不满足以上全部条件时，不创建 ADR。已有用户文档或 Issue 已经完整记录的内容不得机械复制到 ADR。

## 处理 ADR 冲突

如果拟议变更与既有 ADR 冲突，必须明确指出冲突、引用对应 ADR，并说明重新讨论的理由，不得静默覆盖既有决策。
